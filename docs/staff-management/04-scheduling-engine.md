# 排班引擎設計

## 輸入與輸出

輸入為門市、週期、營業日曆、班次模板、啟用員工、可上班時段、休假/偏好、技能、已發布承諾、A~E 快照與週末公平 ledger。輸出為草稿班表、未滿足 constraint、每筆指派 reason codes、品質指標與固定 seed。

## Hard constraints

1. 週一為休店日，不建立一般班次。
2. 週二至週五每個營業時間片恰有 1 名合格員工。
3. 週六、週日每個營業時間片恰有 2 名合格員工。
4. 營業期間不得有 coverage gap。
5. 員工只可排在已聲明可上班且未核准休假的時段。
6. 同一員工班次不得重疊，且符合休息、工時與連續工作日政策。
7. 需要特定技能的班次至少有一名具資格員工。
8. 已鎖定或已開始班次不可由重算移除。

## Soft constraints（由高到低）

1. 修復週末機會債務與長期分布差距。
2. 滿足員工明示偏好與避免日期。
3. 平衡總工時、週末工時及開/關店負擔。
4. 參考 A~E 與班次適配，但限制其對公平性的最大影響。
5. 減少發布後變更與碎片班。

## 求解流程

1. 驗證輸入 completeness 與門市 scope。
2. 依日曆產生 coverage slots；週一 slots 為 0。
3. 建候選邊 `(staff, slot)`，先排除 hard constraint 不合格者。
4. 以 constraint solver/min-cost flow 最小化 soft penalty。
5. 完整驗證 coverage、重疊、休息與資格。
6. 產生草稿與 explanation；若不可行，回傳最小衝突集合，不發布部分結果。

## 發布與重算

- 狀態：`DRAFT → VALIDATED → PUBLISHED → SUPERSEDED/ARCHIVED`。
- 發布必須帶 expected version，避免兩位管理者覆蓋。
- 變更已發布班表會建立新 revision；舊版唯讀。
- 緊急缺勤只重排受影響 slots，優先保留其他承諾。
- 引擎相同 input hash、policy version、seed 應產生相同結果。

## 無解處理

- UI 顯示具體缺口，例如「週日 14:00–18:00 需要 2 人，只有 1 名可用且具資格」。
- 建議依序：徵詢自願、允許管理者進入候補、跨店支援（未來）、調整營業時間（需額外授權）。
- 絕不以忽略休假、超時或資格限制來強行生成「成功」班表。
